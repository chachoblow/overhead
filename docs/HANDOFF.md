## Element persistence ([0079](decisions/0079-fetched-element-persistence.md)) — done this session
- `firmware/src/element_store.rs` (host-tested: CRC, header, slot choice, every interrupted-save point), `firmware/partitions.csv` (`elements` 0x7b0000+0x50000, factory app 7,808 KiB), `Schedule::resume_stored`, `Cause::Store`; runtime load/save in `firmware/src/live_radar.rs` via `esp-storage` (bounce buffer in internal RAM). **Flash every runtime image with `--partition-table partitions.csv`**; `espflash flash` keeps the stored copy, `erase-region 0x7b0000 0x50000` clears it. [Evidence](../firmware/README.md#element-persistence-0079): erased → fetch → save; reset → load, no request; refresh → save other slot (store gap 11.8 ms, no skipped frame, heap flat); corrupt slot → fallback → fetch; device app refresh saved seq 4 and a user reset came back without a request.
- **Open concern:** the user found the device app at `NO FRAME` at ~04:05 UTC on 2026-11-06 (running at 01:17, unobserved after). Likely lapsed SNTP (network, or a KoD that stops queries until reboot), not shown. The 12-hour non-resetting capture that followed (04:08–16:08 UTC, local `firmware/target/device-overnight.log`, read) was clean: no `NO FRAME`, KoD or Wi-Fi drop; one refresh at 09:17 UTC, 156/156, `STORE saved slot=1 seq=5`. Cause still unknown; nothing captured since.
- **KoD lead (user, 2026-11-06):** on `QueryResult::KissOfDeath` the SNTP loop in `firmware/src/live_radar.rs` (~l. 679) prints `SNTP KoD: stop queries until reboot` and parks forever. Fetches are driven from that loop, so element refreshes stop too, and once the holdover lapses the device shows `NO FRAME` until a reboot. Unproven for this incident: the overnight capture began after the reset that would have cleared it (no `KoD` lines through 14:40 UTC, one clean refresh at 09:17 UTC saving `slot=1 seq=5`), and the user's first reset reportedly did not recover the display. Parking forever is a defect regardless: a fix (bounded back-off after KoD, fetch scheduling independent of SNTP replies) changes recorded behaviour and needs a new decision.
