# Frozen M2 suite — first accepted S3 captures

2026-10-11 UTC, with explicit approval for two flashes and two reset-separated
captures per image. **All frozen target evidence gates pass.** This does not close
M2: operating limits/cadence/over-budget policy and bounded scheduling verification
remain open. No extra cases, source refresh, heap enlargement, dependency/toolchain
change or firmware change during capture.

## Evidence and acceptance

- [Raw logs, provenance and regeneration](s3-m2/README.md).
- [Build/image/source hashes, section/frame inventories and reset commands](s3-m2/artifacts.json).
- [120 individual timing/memory samples](s3-m2/results-samples.csv),
  [per-case min/median/max and collection summaries](s3-m2/results-summary.json),
  [252 individual stack observations](s3-m2/results-stack.csv).
- [Frozen manifest/representation](m2-frozen-manifest.md) and
  [harness, instrumentation boundaries and frame-review limitations](../../firmware/M2_CAPTURE.md).

Timed captures contain all 20 cases, one discarded warmup per case per boot and
three single-invocation measured samples: **120 samples** across two boots.
Diagnostic captures each run all **75 numerical rows**, then one invocation of
each case for each of the two stack patterns. Their timing fields are zero and
are not timing evidence. There were no failed/partial capture attempts, allocation failures,
unexpected rejections, discarded outliers or widened numerical tolerances.

Every complete capture passes strict validation. Accepted IDs/epochs/memberships/
origins, exact owned diagnostics and per-satellite work/completion match the frozen
annex. Heap and collection observations repeat within/between boots and between
timed/diagnostic images. Every pipeline, including document failure, returns both
requested and backend occupancy to zero. Bootloader segments match the exact gated
images; the multiple-DROM diagnostic is absent in all four boots. RWX remains a
separate build warning, not resolved by successful boots.

Hardware: the same ESP32-S3 revision v0.2/8 MB flash, 240 MHz, one CPU, fixed
65,536-byte internal heap. No display, PSRAM or network use. The board now holds
the diagnostic image, idle after completion; reset reruns diagnostics. Monitors
are closed. A future flash/reset still needs approval.

- **Largest peak:** 31,993 requested / **32,124 occupied** bytes, case 06. These
  exact workloads fit the fixed heap; that is not a general 16-satellite device
  limit. Growth is not a per-satellite linear multiplier: 12 and 16 entries have
  nearly equal pipeline peaks, unlike the jumps at 5→9→12.
- **Collection observations:** raw parser-array capacities for growth cases are
  8/16/16/16. Per-record allocation traffic and live occupancy are preserved in
  the logs. Public caller-error/arrival Vec capacities and private collection
  **lengths** are distinguished; no private-capacity inference or host ledger.
- **Density:** case 07 retains 68 passes, more than case 06's 44, but neither its
  retained occupied bytes nor its pipeline peak is the suite maximum. Counts,
  cohort, orbit path, case UTC and memory lifetime are separate dimensions.
- **RAM overlap:** reference JSON adds 3,331 requested / 3,332 occupied bytes;
  densest JSON adds 4,212 in both meters. Dropping after initialization restores
  the flash-control aggregation endpoint, but does not erase the higher pipeline
  peak. Retaining through aggregation gives the highest endpoint: **21,148 B**.
- **Diagnostics:** equivalents retain all four memberships; conflict omits 6251
  without older fallback; invalid records retain one caller and one core error.
  The failed document publishes no catalogue, skips aggregation, retains its
  owned failure message (48 live requested/occupied bytes), and fully releases it.
- **Partial work:** allowance 1,000 is incomplete, not a global next-pass result.
  Zero allowance still materializes unsearched reports and occupies 12,312 B at
  aggregation end. These are controlled outcomes, not product overload policy.

Case 06 initialization median is 64.310 ms; aggregation ranges from
25.566998–25.579120 s. Case 13 parses all 32 records and has the slowest initialization
median, 152.345 ms, despite only eight accepted objects. The empty flash-copy phase
also has timer/harness overhead; don't interpret it as data transfer throughput.
Historical case 02 retains the earlier target's 16,024-byte initialization peak
and 8,088-byte aggregation endpoint, but the new instrumented timing is not the
old binary's timing. Historical and expanded cohorts retain different frozen UTCs;
comparisons are not controlled solely for catalogue size.

## Independent numerical and written-stack gates

All **75 selected numerical rows pass in each diagnostic boot** with unchanged
strict tolerances: 12 original TEME rows, 9 rotation, 13 geodetic, 27 isolated
geometry, 12 ISS pipeline and 2 Vanguard pipeline rows. Work-count agreement is
separate evidence; it does not replace these checks or the existing independent
[pass-detection study](detection-intervals.md). This validates the selected numerical
cases, not live orbit freshness or arbitrary pass-detection accuracy.

For each applicable case/phase there are four observations: two patterns × two
boots. All four observed depths agree for each case/phase. Both patterns in both
boots pass the known-local smoke test: baseline 2,656 B versus loaded 10,604 B
(a 7,948-byte increase), with guard/margin checks passing.

| RAM input copy | 16 | 4,720 |
| Initialization | 80 | 9,168–9,248 |
| Aggregation | 76 | 5,348–7,260 |

The deepest initialization marks are cases 05/06. Depths include live caller/probe
frames and the 256-byte paint safety gap, not just orbit/parser locals. The compiled
frame inventory and unresolved indirect-call/interrupt/unwritten-frame limitations
remain in the [harness review](../../firmware/M2_CAPTURE.md#offline-imageframe-review-and-remaining-limits).
**Do not turn 9,248 B into a safe/worst-case stack allocation.**

## What this enables next

The frozen target-capture block is complete, without extending its matrix.
Use this bounded evidence to decide initial input/group/record/accepted-satellite/
stored-result limits, lookahead, recomputation cadence and explicit over-budget
behavior. The 64 KiB heap is already reserved in `.bss`; occupied bytes are not
extra static RAM. Display/application, network/TLS/refresh and whole-device peaks
remain unmeasured and require headroom, not optimistic subtraction.

A synchronous ~25.6-second search cannot share a 50 ms/20 Hz display loop. Scope
and verify bounded scheduling latency separately; no executor, second core,
resumable architecture, safe stack size or production default is selected here.
No additional measurement matrix without a specific unanswered decision.
