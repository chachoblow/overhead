# M4 coastline — Stage A measurement protocol and capture

Started 2026-10-22; **Stage A S3 RAM-target capture on 2026-10-23 failed the provisional coast-time gate**. Offline link/image comparisons and the separately authorized two-image device capture are recorded below. No Sharp hookup, physical-panel review or new operating budget is reported here. The current [S3 firmware](../../firmware/README.md) is an isolated M2 kernel benchmark, not a radar/display app; the documented display is disconnected. The [host cost preflight](m4-coastline-host-cost-preflight.md) is not target evidence. [0055](../decisions/0055-defer-all-view-coastline-proof-for-m4.md) defers all-view proof for this iteration, not the device gates or investigation of a reproduced visible omission.

## Measurement question and permission boundary

Can the *unchanged* [0054 wide-only comparison](../decisions/0054-first-executable-coastline-comparison.md) meet the [provisional M4 measurement gates](m4-coastline-budget-preflight.md) on an S3, and can a later Sharp-backed whole-device frame remain legible and responsive? These are **two different experiments**. First, propose an isolated target renderer measurement with a 400×240, 1-bit in-memory draw target; then assess actual Sharp output and the complete app/frame on hardware. Stage A has measurement-only source and a captured target experiment; Stage B is not implemented. The recorded approval covered only the specified Stage A builds and two-image capture; obtain **new approval before any further target build, flash, toolchain change or hardware access**. Flashing also changes the board's existing image. Do not refresh or repurpose the [frozen M2 captures](s3-m2/README.md) as current coastline measurements.

## Stage A — fixture and measurement contract

`render/src/measurement.rs` exposes opt-in coast/frame paths and an injected late-failure hook; `firmware/src/coast_measurement.rs` contains a parsed ISS fixture, a 1-bit RAM target type, ten named observer/FOV cases plus a computed ISS-ground selected control, and host tests. The `coast_main.rs` image holds two 12,000-byte static targets (draw and untimed pixel reference). `firmware/src/coast_main.rs` is a separate measurement image source; its release ELFs and first S3 capture are inspected below. The opt-in firmware features `coast-measurement` and `coast-measurement-on` select the control/on paths. Historical kernel binaries do not depend on them. Optional app/render/embedded-graphics dependencies let the isolated firmware use the existing platform-agnostic code and draw-target trait; their versions already exist in the host workspace, but their transitive packages add entries to the evolving firmware lockfile. This does not update the pinned frozen-M2 revision.

The host checks exercised the fixture and rollback; the authorized Xtensa link and image-gate inspections below do **not** execute target timing, stack, heap or Sharp measurements. The first pair retained coast code in the off path; the second pair corrected that comparison control.

1. Pin the prospective source revision, export hash, compiler/toolchain and release settings, board/clock, target, input cases, display-target implementation and image hash for every run. Keep `overhead-render`/`overhead-app` platform agnostic. Any new *measurement-only* firmware entry point and build feature should remain distinct from historical M2 binaries and use the same current renderer code path. Decide how to supply a deterministic catalogue/app sample without adding a live fetch or silently changing its source. The one-ISS host fixture is a control, **not** a production population or frame workload.
2. Reuse the host probe's named observer/FOV suite as a minimum: SF 0.1°/1°/5°/100°, Colorado 20°, polar 20°, dateline 5°, plus the exported-segment limb 20°/100° and tight horizontal viewport-edge observers. The computed ISS-ground case ensures a selected frame alongside empty cases; post-ink selected and warning cases now have an untimed byte-for-byte immediate-failure control. A successful-coast geographic pixel reference and a representative device population remain outside this isolated fixture. Record observer coordinates, exact FOV and which scenes actually draw ink; boundary cases are finite stress samples, not worst-case coverage. Validate target outputs against no-coast/`COAST ERROR` controls where possible, not just elapsed time.
3. For each scene measure one **complete successful `coast::draw` invocation**, including checked-asset validation, projection/clipping and writes to the chosen 1-bit target. Also measure complete `draw_frame` with and without coast using the same target and app sample, with setup/warm-up and UART outside timed regions. Retain **individual** repeated samples, sample count and maximum observed invocation, not just medians or a subtraction of two unrelated maxima. Expose/measure a no-coast control without making normal rendering skip a coast failure. Track display writes separately; a RAM target does not measure Sharp SPI transfer or refresh.
4. The feature-gated `measurement::frame_late_failure` uses the existing private draw-hook seam: after at least one coast On write and 20,000 interpolation intervals it fails coast-only, causing clear/repaint and `COAST ERROR`. Production's constant-false path remains unchanged. The proposed target invocation times the **complete polar and selected ISS-ground failed frames**, warning-free and with an ingestion warning, not only the first pass; host tests compare each byte-for-byte with an immediate-failure foreground/notice control. The measurement-only target path performs the same control outside timing on a second 12,000-byte static screen. Target execution and inspection remain open. The early invalid-asset path is not a late-failure cost and is not measured by this harness. Report whether a naturally occurring numeric failure was found; injection is not proof of its frequency or cost.
5. Once authorized, produce comparable **coast-on and coast-off release ELFs** with identical app fixture, target, flags, display target and instrumentation other than the `coast-measurement-on` feature. Confirm the no-coast image actually excludes coast data and code (and the coast image retains them); compare allocated flash sections and application image bytes, with section/symbol breakdown for the 15,484-byte asset and code/tables. Record build commands and ELF/image hashes. Account for alignment, dead-code elimination and measurement hooks; a difference is *incremental compiled contribution in this harness*, not the device's remaining flash space. Apply the existing [offline image gate](../../firmware/IMAGE_GATE.md) to the **exact normal image** before any proposed flash; its stress/negative-control artifacts are not flash candidates. A passing image gate is not permission to flash.
6. The proposed target entry point uses the existing optional 64 KiB metered allocator for fixture setup and checks zero allocation calls during each draw, and reuses the existing stack watermark with a pre-run known-local smoke check. Compare observed writes for matched with/without-coast calls under confirmed exclusive stack ownership. The existing [written-stack watermark](../../firmware/src/stack_watermark.rs) requires exclusive CPU0 stack ownership and measures observed writes, **not** a safe worst-case bound. State probe overhead, patterns and absolute readings; do not subtract separately observed peaks and present the result as guaranteed live scratch. Inventory any persistent coast buffer and static RAM separately. A full wide 1-bit buffer alone is 10,560 B (12,000 B for 400×240), not a free coastline scratch allowance. The second 12,000-byte measurement-only reference buffer is present in both proposed images; confirm that fact in the ELFs and report both buffers' static RAM separately.

**Screening report:** compare the largest observed *complete successful coast rebuild* against the provisional ≤5 ms at 240 MHz, the incremental compiled coast contribution against ≤64 KiB (including ≤32 KiB asset), observed coast-attributable internal scratch against ≤1 KiB, and coast dynamic heap against 0 B. Report late-failure full-frame timing and memory separately; it cannot be substituted for the successful gate. A sample maximum is not a hard worst-case bound. If a gate fails or a metric cannot be isolated reliably, report that plainly and revisit the candidate/measurement design; do not shorten strokes, silently omit geography, or weaken [0053's known-gap rule](../decisions/0053-no-resolvable-coastline-omissions.md).

## Stage B — separate Sharp and whole-device assessment

After an approved display hookup and an app/display integration plan, measure actual 400×240 1-bit transfer/refresh, complete coast-enabled and coast-free frame latencies, app update, concurrent/competing work and task/interrupt stack use with representative curated populations. Record end-to-end frame-time distributions and missed-frame behavior against the **50 ms nominal period** (20 Hz intent), not a claim that Stage A's 5 ms leaves 45 ms free. Check late-failure repaint on the real output path: the current renderer clears and repaints a draw target, which does not by itself guarantee an atomic visible frame on a physical panel. Review legibility on the actual Sharp at native size across tight/local/overview zoom, selected/empty/notices, and awkward limb/viewport scenes. Record user assessment independently of timing and host/simulator appearance; keep square/circular baselines intact. Do not infer whole-device headroom from the isolated M2 kernel, a RAM framebuffer, a host SDL screenshot or an offline image gate.

## Review / stop conditions

Before building Stage A, review whether the proposed target can link the shared app/renderer and fixtures without modifying historical benchmark semantics, how its coast-off binary is made genuinely comparable, how the measurement-only seam and draw target preserve production behavior, and how stack/heap observations will be delimited. If any needs a new dependency, justify it first; do not guess rapidly changing target APIs. Stage B additionally needs a display hookup/transfer and buffering decision, plus hardware access approval. The offline harness and protocol do not authorize either target measurement stage, adopt the coastline as a device asset, close M2 operating budgets or certify all-observer coastline completeness.

## Offline source review — 2026-10-22

**No-go for a target measurement image as written; no target build or hardware access was performed.** The host feature-gated firmware tests (10 passed), renderer late-failure test and workspace check passed during this review. Host compilation does not compile the Xtensa-only `coast_main.rs` entry point.

- **Definite target compile blocker:** `firmware/src/coast_main.rs` calls `esp_alloc::HeapRegion::new` with only a pointer and size. The pinned `esp-alloc` 0.11.0 API requires a third capabilities argument; `firmware/src/catalogue_main.rs` supplies `MemoryCapability::Internal.into()`. Fix and review this before asking for a target build. No other target compile/link claim follows from host tests.
- **Image-comparison gate:** the coast-off entry point calls `frame_off` and intends to drop the coast path, but source/host tests cannot establish that release linking excludes the asset and code. Separately build and inspect the two otherwise identical release ELFs, sections and image bytes only after target-build approval; gate the exact prospective flash image under [IMAGE_GATE](../../firmware/IMAGE_GATE.md) before any separately approved flash.
- **Output controls:** the host test checks an injected post-ink failure against a no-coast foreground/notice frame, but the proposed target image has no corresponding expected-pixel comparison; its `Late` mode covers only unselected, warning-free polar 20°. `FrameOn` reports completion without asserting that coast actually succeeded, and `Coast` draws repeatedly onto the reused screen without clearing it, so a coast-only checksum is not a fresh per-scene pixel control. Add target pixel/notice checks and selected/warning late-failure cases before interpreting a complete Stage A capture. Keep counted On writes and scene coordinates; a checksum alone does not establish correct coast geometry.
- **Memory interpretation:** the timed draw is bracketed by the allocator meter and stack watermark, but this entry point has not run the existing target stack self-check, proven exclusive CPU0 stack ownership at runtime, or reported probe bounds/patterns. The 12,000-byte static screen and 64 KiB reserved heap are baseline memory, not coast scratch. Record absolute matched observations and static inventory, not a subtraction of unrelated peaks or a safe stack bound.

The shared frame/coast call paths and the one-ISS fixture are suitable *proposals* for isolated controls, not evidence of S3 viability or a representative device workload. Stage B Sharp/whole-device assessment remains a distinct later gate.

**Offline source follow-up, same date (before target-build approval):** the pinned allocator call now supplies `MemoryCapability::Internal`; coast-only timed samples clear the reused target *before* timing, and `FrameOn` reports coast success rather than assuming it. The target image has selected/empty, warning/no-warning late-failure modes and compares their final pixels byte-for-byte with a separate immediate-failure frame outside sampling. Both feature variants use a second 12,000-byte screen for controls, and the stack probe now runs the existing known-local self-check and prints baseline bounds. Host tests passed; no target execution or hardware access occurred. The rollback control is not a coast-on geographic reference. Do not change 0053's known-gap rule or treat frozen M2 captures as coast measurements.
