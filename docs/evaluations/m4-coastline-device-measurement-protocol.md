# M4 coastline — offline Stage A harness and device-measurement protocol

Date: 2026-10-22. **Offline Stage A harness implemented for review:** no target build, flash, capture, Sharp hookup, physical-panel review or new operating budget is authorized or reported here. The current [S3 firmware](../../firmware/README.md) is an isolated M2 kernel benchmark, not a radar/display app; the documented display is disconnected. The [host cost preflight](m4-coastline-host-cost-preflight.md) is not target evidence. [0055](../decisions/0055-defer-all-view-coastline-proof-for-m4.md) defers all-view proof for this iteration, not the device gates or investigation of a reproduced visible omission.

## Measurement question and permission boundary

Can the *unchanged* [0054 wide-only comparison](../decisions/0054-first-executable-coastline-comparison.md) meet the [provisional M4 measurement gates](m4-coastline-budget-preflight.md) on an S3, and can a later Sharp-backed whole-device frame remain legible and responsive? These are **two different experiments**. First, propose an isolated target renderer measurement with a 400×240, 1-bit in-memory draw target; then assess actual Sharp output and the complete app/frame on hardware. Stage A now has measurement-only source, not a tested target image; Stage B is not implemented. Review the fixture and instrumented build design; obtain **separate approval before any target build, flash, toolchain change or hardware access**. Flashing also changes the board's existing image. Do not refresh or repurpose the [frozen M2 captures](s3-m2/README.md) as current coastline measurements.

## Stage A — offline harness, not a target measurement

`render/src/measurement.rs` exposes opt-in coast/frame paths and an injected late-failure hook; `firmware/src/coast_measurement.rs` contains a parsed ISS fixture, a 12,000-byte static 1-bit RAM target, ten named observer/FOV cases plus a computed ISS-ground selected control, and host tests. `firmware/src/coast_main.rs` is a separate, unbuilt measurement image source. The opt-in firmware features `coast-measurement` and `coast-measurement-on` select the control/on paths. Historical kernel binaries do not depend on them. Optional app/render/embedded-graphics dependencies let the isolated firmware use the existing platform-agnostic code and draw-target trait; their versions already exist in the host workspace, but their transitive packages add entries to the evolving firmware lockfile. This does not update the pinned frozen-M2 revision.

The host checks exercised the fixture and rollback; **no Xtensa compile/link, ELF-size comparison, image gate, target timing, stack, heap or Sharp measurement has run**. Target-only allocator/stack/link behavior and the comparability of the two release images must be reviewed before requesting any target build.

1. Pin the prospective source revision, export hash, compiler/toolchain and release settings, board/clock, target, input cases, display-target implementation and image hash for every run. Keep `overhead-render`/`overhead-app` platform agnostic. Any new *measurement-only* firmware entry point and build feature should remain distinct from historical M2 binaries and use the same current renderer code path. Decide how to supply a deterministic catalogue/app sample without adding a live fetch or silently changing its source. The one-ISS host fixture is a control, **not** a production population or frame workload.
2. Reuse the host probe's named observer/FOV suite as a minimum: SF 0.1°/1°/5°/100°, Colorado 20°, polar 20°, dateline 5°, plus the exported-segment limb 20°/100° and tight horizontal viewport-edge observers. The computed ISS-ground case ensures a selected frame alongside empty cases; warning-frame measurement and on-target pixel/notice controls remain to be added before complete Stage A acceptance. Record observer coordinates, exact FOV and which scenes actually draw ink; boundary cases are finite stress samples, not worst-case coverage. Validate target outputs against no-coast/`COAST ERROR` controls where possible, not just elapsed time.
3. For each scene measure one **complete successful `coast::draw` invocation**, including checked-asset validation, projection/clipping and writes to the chosen 1-bit target. Also measure complete `draw_frame` with and without coast using the same target and app sample, with setup/warm-up and UART outside timed regions. Retain **individual** repeated samples, sample count and maximum observed invocation, not just medians or a subtraction of two unrelated maxima. Expose/measure a no-coast control without making normal rendering skip a coast failure. Track display writes separately; a RAM target does not measure Sharp SPI transfer or refresh.
4. The feature-gated `measurement::frame_late_failure` uses the existing private draw-hook seam: after at least one coast On write and 20,000 interpolation intervals it fails coast-only, causing clear/repaint and `COAST ERROR`. Production's constant-false path remains unchanged. The proposed target invocation times the **complete polar failed frame**, not only the first pass; the host test compares it pixel-for-pixel with an immediate-failure foreground/notice control. Selected/warning late-failure cases and a target pixel control remain follow-ups. The early invalid-asset path is not a late-failure cost and is not measured by this harness. Report whether a naturally occurring numeric failure was found; injection is not proof of its frequency or cost.
5. Once authorized, produce comparable **coast-on and coast-off release ELFs** with identical app fixture, target, flags, display target and instrumentation other than the `coast-measurement-on` feature. Confirm the no-coast image actually excludes coast data and code (and the coast image retains them); compare allocated flash sections and application image bytes, with section/symbol breakdown for the 15,484-byte asset and code/tables. Record build commands and ELF/image hashes. Account for alignment, dead-code elimination and measurement hooks; a difference is *incremental compiled contribution in this harness*, not the device's remaining flash space. Apply the existing [offline image gate](../../firmware/IMAGE_GATE.md) to the **exact normal image** before any proposed flash; its stress/negative-control artifacts are not flash candidates. A passing image gate is not permission to flash.
6. The proposed target entry point uses the existing optional 64 KiB metered allocator for fixture setup and checks zero allocation calls during each draw, and reuses the existing stack watermark. Compare observed writes for matched with/without-coast calls under confirmed exclusive stack ownership. The existing [written-stack watermark](../../firmware/src/stack_watermark.rs) requires exclusive CPU0 stack ownership and measures observed writes, **not** a safe worst-case bound. State probe overhead, patterns and absolute readings; do not subtract separately observed peaks and present the result as guaranteed live scratch. Inventory any persistent coast buffer and static RAM separately. A full wide 1-bit buffer alone is 10,560 B (12,000 B for 400×240), not a free coastline scratch allowance.

**Screening report:** compare the largest observed *complete successful coast rebuild* against the provisional ≤5 ms at 240 MHz, the incremental compiled coast contribution against ≤64 KiB (including ≤32 KiB asset), observed coast-attributable internal scratch against ≤1 KiB, and coast dynamic heap against 0 B. Report late-failure full-frame timing and memory separately; it cannot be substituted for the successful gate. A sample maximum is not a hard worst-case bound. If a gate fails or a metric cannot be isolated reliably, report that plainly and revisit the candidate/measurement design; do not shorten strokes, silently omit geography, or weaken [0053's known-gap rule](../decisions/0053-no-resolvable-coastline-omissions.md).

## Stage B — separate Sharp and whole-device assessment

After an approved display hookup and an app/display integration plan, measure actual 400×240 1-bit transfer/refresh, complete coast-enabled and coast-free frame latencies, app update, concurrent/competing work and task/interrupt stack use with representative curated populations. Record end-to-end frame-time distributions and missed-frame behavior against the **50 ms nominal period** (20 Hz intent), not a claim that Stage A's 5 ms leaves 45 ms free. Check late-failure repaint on the real output path: the current renderer clears and repaints a draw target, which does not by itself guarantee an atomic visible frame on a physical panel. Review legibility on the actual Sharp at native size across tight/local/overview zoom, selected/empty/notices, and awkward limb/viewport scenes. Record user assessment independently of timing and host/simulator appearance; keep square/circular baselines intact. Do not infer whole-device headroom from the isolated M2 kernel, a RAM framebuffer, a host SDL screenshot or an offline image gate.

## Review / stop conditions

Before building Stage A, review whether the proposed target can link the shared app/renderer and fixtures without modifying historical benchmark semantics, how its coast-off binary is made genuinely comparable, how the measurement-only seam and draw target preserve production behavior, and how stack/heap observations will be delimited. If any needs a new dependency, justify it first; do not guess rapidly changing target APIs. Stage B additionally needs a display hookup/transfer and buffering decision, plus hardware access approval. The offline harness and protocol do not authorize either target measurement stage, adopt the coastline as a device asset, close M2 operating budgets or certify all-observer coastline completeness.
