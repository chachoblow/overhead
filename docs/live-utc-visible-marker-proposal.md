# M6 visible-marker device diagnostic (no visual observation)

Status: one exact-image flash and bounded UART capture completed on 2026-10-27 after explicit approval; **the user was not watching the panel, so no visual result was observed**. This does not amend [0067](decisions/0067-opt-in-live-utc-iss-radar-scope.md) or select a standalone-device contract.

## Evidence and goal

The [first live-UTC candidate](../firmware/README.md#live-utc-iss-radar-candidate-flashed-bounded-uart-capture) used 2026-10-04 ISS elements. Its empty view at the sampled UTC is explained headlessly by a successfully propagated object below the fixed observer's horizon. A separately retrieved 2026-10-26 CelesTrak ISS OMM, first tested as an ignored host input and later pinned for this diagnostic, gives a visible selected marker at the same fixed observer and 5° wide view at 2026-10-27 02:39 UTC. This is a modelled window, not a device observation; an old-element run also happens to show a marker at that instant. The retained OMM's provenance, SHA and host results are in the firmware guide. None of these results demonstrates current on-panel tracking.

Goal: one bounded physical observation of a marker and its natural-speed movement under screened live UTC, with a separately named opt-in image and a single locally pinned ISS OMM. This is not a production element source, location choice or runtime age policy.

## Suggested boundaries and gates

1. The user authorized pinning the [2026-10-26 OMM](../firmware/fixtures/README.md) and staging the separate image at the original fixed observer/5° wide view. Re-evaluate an upcoming above-horizon **and in-view** interval against those exact bytes before any device trial. Do not reuse a past predicted window as a promise. Never rewrite the M2 freeze or silently substitute the source in the existing `live-utc-radar` image.
2. The separately named opt-in image was built and flashed once with explicit approval. It retains 0067's screened UTC, `NO FRAME`, independent display/SPI owner, command-side schedule and failure behavior, swapping only the pinned elements. No HTTPS, persistence, automatic refresh, controls, source-age cutoff or new cadence. Historical and original live-UTC images remain distinct build targets.
3. Host-test the exact new source through catalogue ingestion, app propagation/visibility, wide renderer, cached frame and selective sender at an empty time, a positive marker time and nearby motion times. Verify source identity/epoch, observer/view, predicted interval, notice/marker/selection and rendered pixel changes; host tests do not establish real-world orbital accuracy or physical COM edges.
4. A target build requires the existing local toolchain and build-time Wi-Fi credentials; never commit credentials, ELF, image or raw logs. Before any flash, run the exact-ELF/image offline gate, check size and MAC, and request **explicit separate approval to flash** that image. A newly built image must be re-gated. Ask the user to inspect the panel during a **newly validated** visibility interval, then bound the UART capture; report missed window, no sync, blank panel and failure as such. Do not leave a long-running unattended capture or claim physical COM-edge/20 Hz/extended-service evidence from it.

Host preflight and the separate gated credential-bearing build led to **one explicitly authorized flash**. The [firmware guide](../firmware/README.md#pinned-omm-live-utc-marker-diagnostic-flashed-no-visual-observation) records the exact hashes, dated host window, board checks and bounded UART-only evidence. The user was not watching during that window; the predicted window is expired and **there is no physical marker/motion proof**. The user also declined another long wait. No *further* board access/flash is authorized by this document. Before proposing another trial, agree an actual time when the user is ready to inspect the panel; do not schedule another long unattended wait.
