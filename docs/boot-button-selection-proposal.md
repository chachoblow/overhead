# BOOT-button selection — bounded host-first proposal

Status: **in-view cycling, one-event-per-completed-debounced-press and ignoring presses without a valid frame agreed; a separately approved fixed-historical target image logged two in-view BOOT selection advances, both visually confirmed by the user**. The user approved provisional active-low BOOT/GPIO0 and 20 ms qualification for offline-build-only integration; physical input timing remains unverified. This is a bounded behavior outline for the first M6 BOOT-button prototype, not a GPIO or scheduling contract. The knob remains a separate zoom input under [0060](decisions/0060-defer-timing-to-physical-prototype.md).

## Agreed selection behavior

The user confirmed that BOOT should cycle **in-view eligible markers only**, like simulator Tab and [`RadarApp::select_next()`](../app/src/lib.rs). Keep [0049's wide-view selection rules](decisions/0049-stable-wide-selection.md): ascending NORAD ID with wrap; never cycle through off-screen arrows, failed/below-horizon objects or a marker with invalid projection. A retained successfully tracked, above-horizon off-screen selection remains selected when nothing is in view. With no retained selection and no in-view marker, remain unselected. With one in-view marker, a cycle selects or retains that one. With multiple in view, a cycle advances from the current ID to the next higher in-view ID or wraps to the first. An off-screen retained ID advances to the next higher **in-view** ID, wrapping if necessary. Frame update, zoom, time loss and genuine tracking loss still follow existing app rules; BOOT must not manufacture a frame or restore stale selection.

The selection agreement itself does not dictate input timing or hardware; the provisional GPIO0/20 ms diagnostic choices below are not a validated device policy.

## Agreed input behavior; implementation details remain open

The user approved **one cycle per completed, debounced press**, with no auto-repeat while held, and approved ignoring presses when the app has no valid frame (no queued selection on recovery). The host-tested `poll_selection` boundary consumes a completed event and calls `select_next()` once only for a valid frame; after UTC recovery the normal first-in-view acquisition applies. It does not modify catalogue, physical samples or UTC. If a press occurs during a blocked display operation, do not claim it was captured or serviced until an input sampling/queue policy is chosen. The opt-in diagnostic uses active-low GPIO0 with pull-up and a provisional 20 ms interval, but boot-time behavior and event buffering/latency still need physical review; it adds no dependency.

## Host coverage and remaining validation

- Multi-marker wide frame: repeated requests walk ascending IDs and wrap; no request leaves selection unchanged. Off-screen arrow IDs are skipped. From a retained off-screen ID, select the next higher in-view ID or wrap.
- Single in-view marker: requests remain on that ID (including when the previous selection was off-screen). Zero in-view: keep a valid retained off-screen selection, otherwise remain unselected; returning to an in-view frame follows 0049's acquisition rule.
- After selected-object horizon crossing, tracking failure, catalogue removal or invalid/no-UTC frame: no old selected data returns. A request with no valid frame has no effect. Recovery acquires only a current in-view eligible marker.
- The pure [`CompletedPress`](../firmware/src/button_input.rs) filter and host-only selection composition are implemented and host-tested: one event for a qualified completed press, none for startup hold, bounce, hold or repeated polls; clock regression discards a partial press. Composition tests verify multi-object ascending cycling/wrap on the real OMM pool (including a frame update while held), zero-view retention, a single in-view ISS, and that an invalid-frame press is consumed while recovery follows ordinary acquisition (including time loss during a press). The interval is injected into the filter; the diagnostic chooses provisional 20 ms, not a measured device threshold. The opt-in [display-owner integration](../firmware/README.md#opt-in-boot-selection-on-the-live-utc-diagnostic-flashed-event-capture) samples at loop boundaries; a press across a frame update or blocking render/SPI might be missed. Physical validation must establish input timing without assuming service latency, and confirm input cannot interfere with `NO FRAME`, COM/refresh or network ownership.
- Square/circular diagnostics remain on their existing visible-only path; knob zoom and physical pass search are unchanged.

Existing selection coverage: `app/src/lib.rs` tests `wide_tab_and_loss_fallback_use_only_in_view_markers` and `wide_selection_survives_zoom_and_replay_motion_but_not_horizon_or_failure`; `sim/src/interactive_tests.rs` checks non-repeating Tab input. Firmware tests cover injected logical levels, times, multi-object OMM pool and single-ISS shared app frames, **not** BOOT GPIO events, multi-object device integration, actual debounce quality or target latency. Workspace check/tests and focused firmware host tests passed for the filter and composition; dummy and credential-bearing target builds passed exact-image offline gates; the approved credential-bearing image booted and acquired UTC, then logged two user-operated BOOT completions while no ISS was in view (`valid=true selected=None`). No in-view target cycling or panel observation follows. A separate [fixed-historical multi-marker image](../firmware/README.md#historical-multi-marker-boot-cycle-diagnostic-flashed-short-uart-capture) passed host pixel-change testing and exact-image offline gating; after separate approval it was flashed and a bounded UART capture logged four in-view markers and two advancing selected IDs. The user reported that the selected label/marker changed on the Sharp panel with each press; this is bounded visual evidence, not a timing or sustained-service proof.
