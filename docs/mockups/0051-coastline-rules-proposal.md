# M4 — Proposed first coastline rules (not approved)

This is a proposal following the [provisional native-size comparison](0051-coastline-legibility-comparison.md), whose **20° appearance** the user said is worth pursuing. That visual feedback does not select the candidate data, thresholds, pixel rules, or implementation. The [accepted camera/limb contract](../decisions/0026-fixed-camera-perspective-slice.md) and [wide layout](../decisions/0033-wide-radar-comparison-contract.md) remain in force until separately amended.

## Recommended first boundary

- Add **surface geography only** in the opt-in 352×240 wide radar; leave square/circular diagnostic output byte-for-byte unchanged. Keep the fixed camera, shared WGS-84 Earth perspective, unfilled limb, observer aim point, catalogue, markers, arrows, counts, selection and five-field strip unchanged. No coastline at all without a valid Earth view.
- Start with the already compared **generalized 1:110m coastline as a provisional candidate**, not an adopted bundled dataset. At a given site, draw only camera-facing WGS-84 zero-height surface segments within the wide viewport. Do not draw far-side land through Earth or reinterpret satellite observer-horizon eligibility as camera occultation. In particular, no filled mask that hides an above-horizon satellite.
- Prefer 1px black strokes on white with no shading/fill. Draw geography with the limb **behind** the aim point, arrows, markers and selected ID; retain the bottom-left white notice backing drawn last. This is a legibility order proposal, not the OR compositing used by the offline mock. Coastline/limb intersections and overlaps with foreground glyphs need pixel review rather than an unexamined assumption that layering alone separates black ink.
- **Reviewed appearance direction:** local coastline detail at 5° matters to the user; they liked the angular treatment at 5°–20° and subsequently said it is fine **throughout the compared 5°–100° range**, including the tiny wide-end texture. Do not propose a tight-zoom suppression or a wide-end cutoff as if either were accepted. This does not specify behavior below 5°, select a simplification method or its parameter values, or authorize rendering. Preserve the limb at every zoom; do not add dithering, grayscale or automatic zoom.
- Require bounded offline preprocessing and a clear data/version/hash record before deciding what, if anything, to ship. A Python mock's 0.2° sampling and its vertex count are **not** a runtime format, memory budget, segment clipping specification or timing result. Choose finite, deterministic near-tangent and viewport segment handling explicitly; avoid drawing a chord across a hidden/back-facing gap or dateline. Do not add a dependency by default.

## Review/implementation gates

1. **Local visual gate reviewed:** the [5° native 1-bit comparison](0052-local-coastline-comparison.md) covers two observers, full/rank-filtered/simplified candidates and a no-coast control with selected/empty radar states. The user likes the simplified *look* tentatively; this does not select its source, rank filter, 2.5px RDP algorithm or implementation. Retain the previously reviewed full-detail 20° reference for context.
2. **Zoom comparisons reviewed:** the [5°–20° progression](0053-coastline-zoom-progression.md) and [40°–100° overview](0054-coastline-overview-comparison.md) established user preference for an angular look throughout the compared range. No visibility cutoff, rank/RDP parameters, source adoption or implementation follows from these images. Before implementation, record the exact zoom policy (including below 5°), source, tangent clipping, pixel order and bounded storage/work in a separate decision.
3. If separately authorized, implement in platform-neutral app/render code with deterministic zoom/site/occlusion, clipping, no-stale-ink and unchanged physical-state tests, plus fresh real-data snapshots, workspace check/tests and app/render no-default-feature checks. Physical-display legibility and S3 cost/capacity remain unverified; do not refresh frozen M2 evidence.

No countdown, normal-view readout, motion slow-down, hardware work, source adoption or renderer implementation is authorized by this proposal.
